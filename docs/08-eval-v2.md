# Eval v2：从"关系真伪"到"用户价值"指标

> 生成：2026-08-26 · 配套：docs/06-eval-report.md（v1：关系精度）
> v2 回答的问题从"我写进去的是不是错的？"升级为"**用户漏掉多少？发现多快？误报多少？**"

---

## 1. 指标定义

| 指标 | 定义 | 测量方式 |
|------|------|---------|
| Relation Recall | 已知真实关系中库覆盖的比例 | 已知关系基准集 vs 库内覆盖 |
| Event Recall | 已知重要事件中库覆盖的比例 | 已知事件基准集 vs 库内事件 |
| Time-to-detection | 事件发生 → 进入系统的时间差 | 回溯（历史事件）+ live（cron 启动后自动记录） |
| False alert rate | watchlist 推送中假阳性的比例 | live 运行后统计 |
| Evidence coverage | claims 带来源的比例 | evidence-audit 输出（当前 98%） |

**诚实声明**：以下为**回溯覆盖延迟**（库建于 2026-08-26，历史事件是补录的），不是 live 检测延迟。live 延迟从 cron 首跑（2026-08-28）起记录。

**结论**：回溯补录无法成为商业卖点（补录 ≠ 实时）。**live 指标才是卖点**——cron 已注册（每天 08:00），从 2026-08-28 起：
- 新事件自动记录 `event_date`（发生）与入库时间 → 算出真实 latency
- 目标：重要事件 latency < 24h
